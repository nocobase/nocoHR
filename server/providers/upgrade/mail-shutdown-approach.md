# Mail shutdown: owner decision proposal

**Recommendation:** retain the current production order while correcting business outcome reporting independently. The fixed public interfaces cannot currently provide a safe application-wide drain. Do not install the two-plugin swap or the disproven Jobs-only adapter. A broader ordering experiment would be a separate, isolated feasibility step requiring explicit scope approval, not a production fix.

| Boundary              | Current reverse cleanup                                                                                                                                                               | Required ordering for a safe close                                                                                                            |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| HTTP                  | Standalone or embedded Node host stops admission and awaits admitted requests                                                                                                         | Keep the independently verified host behavior.                                                                                                |
| Application providers | Processes / Assistant / GoLive / native Knowledge / native AI / HR finish before plugin cleanup; HR unregisters subjects and native Knowledge closes its index / subject registration | Preserve each dependency used by an already-admitted mail handler until that handler, its native generation and business writes finish.       |
| Plugins               | Knowledge / Foundation / Agents precede Mail, then Scheduler; Agents stops OnlineAgent before Mail's pending synchronization reaches the recruiting handler                           | Stop new scheduling and await admitted Mail → HR handler → Agents model/result → draft/notification work before releasing those dependencies. |
| Shared services       | File, notifications, authorization and database close later                                                                                                                           | Keep them until task / occurrence writes and accepted terminal-event delivery complete.                                                       |

**Public interfaces and the concrete gap.** `SchedulerService` only exposes `registerTarget()` and `defineSchedule()`. Jobs exposes `getScheduleExecutor('@nocobase/app-plugin-scheduler', scheduler.jobs)` and executor `shutdown()`, but this does not join Scheduler's independent reconciliation or accepted completion reports. That failed concurrency prerequisite is retained in [the contract record](shutdown-drain-contract.md). Mail's public `startSync()` / sync-run reads do not stop all new synchronization or join subsequent application handlers. `application.close()` runs provider cleanup; it cannot supply a pre-cleanup drain from inside that same cleanup. No private token, timer, registry or prototype is an application solution.

**Smallest next scope for a lifecycle change:** first require a public stop-and-await boundary covering scheduling admission, in-flight reconciliation, executor work, state writes, events and accepted reports, while Mail, Agents and application authorization registrations are still available. Only after that contract exists should a thin application pre-cleanup call be proposed, respecting the exact scope and configured Jobs executor and preserving rejection. No such call is installed or requested from an external package in this unit. Merely moving Scheduler to the plugin tail still leaves application-provider teardown before it and is not recommended as a substitute.

**Acceptance after a concrete contract/order is approved:** retain 30 seconds; pair synchronization already running and synchronization arriving during close; use real nonempty recruiting mail with successful and failing local models, partial mail batches, original errors, drafts, task/occurrence terminal states and delivered events. Verify empty work, custom `scheduler.jobs`, duplicate close and rejected close. Correlate each actual dependency release with handler completion; repeat source/build strict startup and the affected close probe once, then the required integrated run. A prerequisite failure stops later candidate checks. No added retry, auto-send, poll, coordinator, persistent state or lock.

**Cost and decision:** this proposal adds no runtime calls because no lifecycle code is installed. A future adapter would add one shutdown-time public drain call, with its waiting reads/writes measured in that implementation; existing in-flight model, draft, task and event costs remain real and are not zero. Per-request/per-poll/claim costs and time budgets must remain unchanged. Owner review is needed before any lifecycle scope or ordering change. Original full-run failures and the specific nonempty counterexample remain open; status reporting does not repair dependency lifetime.

Revalidate the fixed scope, configured executor identity, public failed-result mapping and `ScheduleEnd` meaning whenever Scheduler `.19`, Jobs `.3` or Server `3 beta.2` changes. This unit keeps template `.76`, Skills `.44` and every dependency fixed.
