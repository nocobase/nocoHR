# Mail task and scheduled outcome propagation

Mail task failures now reach the business-mail poll and the existing Scheduler failed result. Production plugin/provider order is unchanged. This repairs misleading success reporting independently of the open background-shutdown boundary.

## Runtime change

- `mail/task-result.ts` wraps only the mail automation boundaries. It captures and rethrows the same work rejection after the existing automation service persists its failed outcome. A recorded pre-work failure propagates a stable local failure without another database lookup. Disabled, duplicate and skipped outcomes remain non-failing. Generic automation completion, ownership, deduplication and retry behavior are unchanged.
- Recruiting sort, application reply and manually linked posting reply use that boundary. A failed nested reply therefore leaves both existing task records failed with the original application-visible error and completion time. No new task is created to report the failure. Existing post-task classification still runs: an unclassified received message becomes unmatched even after failure, so the existing manual re-identification path remains available; linked/partially completed records stay linked. A second classification failure retains both errors locally.
- Billing sort/reply and audit sort had the same discarded-outcome contract and now use the same narrow check. Audit thread replies already reject naturally. At this poll-only delivery, non-poll billing `draftForBill` and audit `draftReply` retained their contracts. The subsequent [non-poll completion unit](mail-completion-unit.md) now propagates billing failures to its existing background catch and corrects the audit pack toast without changing its saved-pack response. Those callbacks do not feed the poll occurrence.
- `mail/service.ts` continues each remaining message/mailbox after a read or handler failure. It retains received counts and original errors in a local aggregate, then rejects once at the end. Successful links, drafts and failed inputs already ingested remain stored. They are not rolled back, retried or replayed by the next poll.
- The HR `app.hr-mail-poll` target maps that aggregate to the already-published `{ state: 'failed', reason: 'MAIL_PROCESSING_FAILED' }`. Successful poll counts keep their original response shape. Scheduler reason contains no body, address or provider error. Jobs can still emit `ScheduleEnd`; the authoritative business outcome is the occurrence's failed status and completion time.
- Manual poll/re-identification/link consumers retain authentication, purpose permissions and existing error boundaries. A handler failure now reaches that error boundary instead of returning a successful count/confirmation; already-saved records stay available on a subsequent read. No public fields or rollback guarantee are added. The existing page error path displays an error rather than its success notification; its refresh behavior is unchanged.

## Validation and evidence

The real production connection uses SQLite, native Mail/local EML, the actual recruiting/automation/HR Scheduler target, real native Agents execution, a local HTTP model and the public Jobs terminal subscription. No external mailbox or model is contacted. The controlled failing model is rejected with HTTP 400 while dependencies are ready; Agents supplies the application-visible `The execution failed.` error. Provider text is not substituted for that existing native error.

The isolated driver accepts `--result success|failure|mixed` and `--revision <commit>`; default behavior remains the successful shutdown prerequisite probe. It archives the chosen runtime revision and copies only verification helpers. The test-only once schedule starts five seconds after registration so its initial firing can be observed; it retains the production target, default Jobs configuration and the original 30-second hook. It waits for the matching public terminal event, not a private state or an assumed poll-call start. Normal calendars and production order are unchanged.

The final failure-first mixed batch runs the real model twice: its first reply fails and its second succeeds, creates one draft and retains the successful native session. Processing continues after the first failure, while the occurrence remains failed. The direct-thread failure branch also verifies anonymous 401, unauthorized-purpose 404, authorized manual poll 500 without provider text, and a subsequent zero-new-mail read with no new model call.

Final results, measured windows and preservation checks accompany delivery. Probe calibration failures are retained separately: an initial driver identifier collision, assumptions about the provider error text and denied HTTP status, and waiting for a poll that could already have started before observation. They are not production regressions. The strengthened probe uses the public terminal event and preserves every original eight-case file-security assertion and business-result safety check.
