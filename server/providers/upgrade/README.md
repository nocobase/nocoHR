## Implemented boundaries

- `server/ai/contracts.ts` owns employee and tool declarations. Existing employee prompts, names, tool schemas and business implementations remain unchanged. The temporary provider adapter registers these declarations with the existing AI runtime.
- `server/providers/assistant/` supplies a LangGraph model/tool turn, a LangChain streaming adapter, durable tool-call storage and a confirmation executor. Employee tool registration, argument validation, server authorization and confirmation policy bound model requests. ASK calls retain their message and model-call identities; only a user decision can execute them. Automatically allowed calls also acquire durable execution state before invoking business code.
- `server/providers/processes/` supplies definition validation, serialized artifact validation, event deduplication and persisted node execution. Before JSON Schema conversion, compilation walks the source contract and accepts only supported declarative JSON types and constraints. Pipe/transform, coercion, catch/prefault, custom checks and overwrites are rejected, including nested ones. Definition changes, unknown node types, unavailable handlers and cycles fail before execution.
- `server/providers/upgrade/` supplies a metadata-only cutover gate and a transactional copy ledger. Replaying a copy preserves subsequent runtime state. Changed source records or missing target records fail verification. Digests distinguish dates, bigint values and ordinary JSON values.
- New migrations create application-owned state only. Rollback refuses populated state instead of deleting it. Historical plugin tables and existing migration sources are unchanged.

An execution error after a possible business write marks a tool call or process as uncertain. It cannot trigger an automatic retry. A process node claimed by a lost worker also cannot be replayed by another engine instance. Drain active work before cutover and resolve uncertain executions individually; automatic takeover, leases and replay are outside the current scope.

## Read-only cutover check

`pnpm nocobase app upgrade-preflight --inventory <path>.inventory.json` reads a metadata inventory inside the application directory. It does not connect to a database. The inventory contains capability identifiers and counts, never credentials, messages, workflow inputs or results. Invalid input produces a fixed diagnostic without echoing its contents.

The AI inventory now also requires `unverifiedToolProfiles` and `autoPolicyDifferences` counts. Previously copied profiles that have not been reconciled against their old effective tools and later edits must be counted as unverified, even when the ledger reports `unchanged`. The CUSTOM/default-ASK/autoCall=true mismatch must be counted as an automatic-policy difference until adapted or explicitly resolved; either positive count blocks cutover. Missing counts invalidate the inventory.

Workflow inventory also requires `unqueuedRuns`, `interruptedNodes`, `unmappedParameters`, `unmappedBranchJoins` and `unverifiedScheduleUsers`. Missing or positive counts block cutover. Accepted work without confirmed native job acceptance and occupied/uncertain nodes require individual reconciliation; repeated submission does not repair them. See [business source inventory and wiring](process-unit.md#business-source-inventory-and-independent-wiring) for the source checks, delegation configuration and minimum deployment mapping evidence. No deployed definition or execution user is inferred from the empty source registry.

The command currently reports the replacement runtimes as unverified even for an empty inventory. A synthetic empty inventory is not evidence that an existing installation has no data. Readiness must be based on an actual installation's metadata, complete capability adapters and integration evidence.

## Remaining integration

### Text and backend confirmation adapter

`AssistantChatAdapter` adapts the text-only subset of the current page protocol: `NocoBaseAIService.sendMessagesStream`, `updateToolCallDecision` and `resumeToolCallStream`. Synthetic requests and events are in `tests/fixtures/assistant-chat-protocol.ts`; behavior tests use the real `AssistantTurn`, `ToolExecutor` and client SSE decoder. The existing page service now selects the configured runtime once per provider instance through authenticated `GET /assistantRuntime`. The page layout and tool-card components are retained.

Automatic calls publish input events before execution and status/results after durable completion. Confirmation continuation publishes stored approval/rejection results before continuing the model. These use the page's existing `tool_calls` / `tool_call_status` events and preserve model-call identifiers in mixed automatic/pending groups. Forbidden and uncertain executions publish errors, with no automatic replay. Event delivery adds no tool-row reads or writes: an automatic call adds two SSE events, each pending call one input event and one terminal event on continuation. No extra HTTP requests or polling are added.

An execution returning `{ status: 'error', content: { code } }` also publishes a page error, while its durable state stays `completed` and its original result remains available to the model. The page receives only a bounded uppercase error code, or `TOOL_BUSINESS_ERROR` for malformed content; arbitrary details, text and stack fields are not copied into the error event. This adds no events or tool-store operations.

Supported process input contracts include JSON scalar types, enums/literals, arrays, tuples, string-key records, unions, nullable values, object-field optionality and JSON defaults. Objects must explicitly reject or retain extra keys (`strictObject` / `looseObject` or a supported catchall); stripping objects are not equivalent after JSON Schema import. String length and unflagged pattern checks, numeric bounds/integer/multiple checks and array lengths are supported. Other string formats, flagged patterns, exhaustive enum-key records, root optionality and source-only wrappers are rejected rather than silently changing parsing. Preflight traverses only the source schema in memory; no runtime database work is added.

### Conversation and request host

`AssistantConversations` now supplies the host rather than accepting a browser-owned session. Migration `202610270033` adds the approved `assistantConversations` and `assistantMessages` tables, plus a nullable automatic-call presentation field on the existing application tool-call table. Historical plugin tables and previous migration files remain unchanged. Rollback refuses populated conversation, message or tool-call state.

Each operation checks the existing `talent.aiAssistant/use` action and filters the conversation by its owning user. Tools retain their existing names, schemas and application implementations. Business services still authorize their own action and record scope as that user. Subjects are resolved afresh for operations and tool execution; no authorization decision is persisted. Code-declared ALLOW tools may execute automatically; ASK tools still require confirmation. Copied employee enablement, tool selections, prompt modes and model allow-lists are applied on this path. Additional installed policies and capabilities still require inventory and reconciliation before cutover.

A conversation has a revision and an active request identifier. A conditional update acquires that exact owned conversation before send, decision or continuation. Concurrent requests fail rather than queue or retry. A consumed client message key or confirmed continuation cannot start another model turn. A crashed request stays occupied after a service restart. There is no expiry, heartbeat, takeover or reset endpoint.

The host appends the user message, model messages and tool results in order. Model call identities are committed before business execution. Serialized messages explicitly retain their IDs because assigning a LangChain message ID after construction does not change its serialized constructor fields. Pending call IDs stay server-owned. A fresh host/database connection can read the transcript and continue a fully decided pending group using stored results. It never invokes those tools again.

Cancellation propagates from HTTP disconnect/stream cancellation to the model. The host retains partial text and any durable business result, then closes the conversation as cancelled or failed. If cancellation arrives during a business action, that action is allowed to finish recording its outcome; it is not replayed or rolled back by aborting the stream. A failed/cancelled conversation remains readable and refuses new turns. Starting another interactive conversation is an explicit user action; unresolved side effects require individual investigation.

### Connected entry points

- `server/routes/assistant.ts` registers authenticated application routes for employee/model lists and owned conversation create/list/read/title/archive/read-status/messages, text send, backend tool decisions and continuation. Security and validation precede SSE. Events use the existing JSON `type`/`body` framing and page decoder. Stream failures contain a fixed code; pre-stream failures use the standard API error body. Archiving retains the underlying history.
- `RuntimeAIService` selects application routes for all conversation identifiers when explicitly enabled. The owned legacy reader queries retained physical tables and checks user/file ownership without retired plugin routes or Collection registration. Uncopied history stays read-only; explicitly copied sessions retain their original identifiers and may continue. The old plugin and its original APIs remain installed until a separately verified cutover; this selector is not a deployment-wide freeze of legacy writers.
- `createAIRunner.reply/structured` uses the application service when registered, including bot replies and automation calls. Structured runs persist their messages in a separate conversation mode, bind no business tools, validate the result and retain the existing one-fresh-session retry/from-text behavior. A page cannot continue a structured session. Weekly certificate briefs also select this path. Explicitly copied legacy session IDs are accepted for the same owner; uncopied sessions remain read-only. No request automatically transfers history.
- The application-owned `ai` configuration resolves copied model metadata using server-only keys. Only the verified `openai-completions` contract is mapped; legacy `openai` uses Responses and is not treated as an alias. Curated model lists, employee restrictions, ordering and sampling parameters are retained. `assistant` retains its explicit single-service fallback. Keys and endpoint URLs never appear in roster/model responses. `@langchain/openai@1.4.7` remains the existing direct dependency, matching core `1.1.49`; no old dependency is replaced. Other providers still require adapters/inventory.

Use this opt-in only in an isolated validation environment until the complete cutover gate passes. Configuration keys and environment variables are declared in `server/config/assistant.ts` and the disabled example in `config.example.yml`. Do not enable it in an existing deployment as part of this source change.

Text with backend tools, owned personal-prompt editing and retained attachment preview are connected. Copied UTF-8 text attachments up to 128 KiB can enter model context; other attachment parsers fail explicitly. New uploads, editing tool arguments, frontend tools, task/system overrides, work context, web search and resend/reconnect remain unsupported and fail closed. Actual browser behavior, installed data/policy inventory and full startup still need integration validation. See [AI history mapping](ai-history.md) for source provenance, copy commands, invariants and costs. The message list has a localized “Continue reply” action for a reopened pending conversation whose last tool group is fully decided. It reads the existing conversation state and terminal history parts; completed/failed/rejected cards are never changed back to pending approval. The action uses the existing tool continuation transport with no browser-supplied results, tool invocation or re-decision. Concurrent continuation still uses the existing server claim. No persistent state or HTTP protocol fields are added; this is a frontend quick change.

### Request costs

Counts below describe the original host without optional configuration/history support, excluding authorization and business-service queries. The additional support reads and current measurements are in [AI history mapping](ai-history.md). Let M be the number of messages appended in the turn, N the pending call group size:

- Create: one conversation insert. List/get/active-state: one scoped read. History: three reads (owned conversation, messages, calls), with no write. Mark-read/rename/archive: one read and at most one conditional update; unchanged values cause no update.
- Send: two host reads, one conditional conversation claim and one final update, plus M message ownership reads/inserts. Add the existing tool costs: each persisted call one insert; each automatic call one read, one conditional tool claim and one result update.
- Decision: two host reads and two conversation updates, plus the existing `2N+1` tool reads and one tool claim; approval also writes the result. Decisions do not append messages.
- Resume: two host reads, `2N` tool reads (pre-stream validation and execution-time validation), two conversation updates, plus M message ownership reads/inserts. Previously decided tools acquire no execution claim and write no result again. New tools requested by the continued model retain normal tool costs.

Each append groups its ownership check and insert in one transaction; tool creation also uses the Repository's transaction. There are no application locks beyond conditional updates, no lease/heartbeat/worker, and no new polling. The page adds one runtime-selection HTTP request per service instance; subsequent selection is cached. Opening/reopening chat now also reads the existing conversation active-state endpoint (one additional GET on reopen; selecting a different conversation already read it). This avoids inferring pending state from terminal cards alone. New-runtime state reads add one SELECT and no writes, locks or transactions; uncopied legacy conversations in the enabled selector stay read-only. Copied sessions use the same state endpoint and original identifiers. The explicit continue action makes one existing resume POST, with no extra decision or execution requests. Default-runtime requests keep their prior paths.

The isolated target SQLite test traces actual SQL, including database-library metadata reads: one pending-tool send uses 20 SELECT, 3 INSERT, 2 UPDATE and 3 BEGIN/COMMIT pairs; approval uses 5 SELECT and 4 UPDATE; continuation uses 22 SELECT, 2 INSERT, 2 UPDATE and 2 BEGIN/COMMIT pairs; history uses 3 SELECT with no write. These are measurements for a single synthetic backend tool, excluding real authorization and HR business queries, not production capacity results. The explicit host append transactions account for additional metadata reads; they must be included when validating a real installation.

### Cutover prerequisites

The foundations are not a complete plugin replacement. Text conversations, message persistence and normal request/confirmation lifecycle now have opt-in entry points. Retained file references, known employee/preferences/model configuration and bounded legacy transcripts have explicit copy paths. New uploads, document parsers beyond bounded text, remaining streaming/page flows, additional providers, installed knowledge/skills/MCP/settings mappings and end-to-end background/Feishu validation remain prerequisites. The bounded process unit now connects validated build artifacts, native Jobs/Scheduler, authorized run APIs and retained terminal history; see [process unit](process-unit.md). Application business definitions and handler bindings, definition/version editing, parameters, custom instructions, complete schedule policy and management pages remain pending.

Historical record mappings require the installed source versions and metadata inventory. Preserve original package namespaces and checksums when retaining migration sources; never re-run their migrations under an application namespace. Drain existing tasks before cutover and require a new user decision for transferred pending tool calls. Unknown capabilities, missing artifacts, missing keys and unexplained historical states prevent switching runtimes.

After both capabilities pass their acceptance checks, remove the old registrations and packages, merge the template's source and compatible dependencies, and run the complete application checks and strict source/compiled startup verification. The template version must change only after that source merge.
